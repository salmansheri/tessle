# Shared schema with Postgres row-level security for Workspace isolation

All platform metadata lives in one Postgres schema with `workspace_id` on every tenant-owned row, protected by row-level security. The app sets the active Workspace per transaction and RLS fails closed when it is unset. We rejected schema-per-Workspace because Flyway migrations and connection handling get painful at many small Workspaces, and rejected application-only filtering because one missed `WHERE` would leak data.

How it is made real: the connection user owns the schema and is a superuser in dev, and both bypass RLS. So every platform transaction runs `SET LOCAL ROLE tessle_app` (a non-owner, non-superuser role) and publishes the authenticated user and active Workspace id from the JWT as transaction-local settings (`TenantTransactionManager`). Policies read them through helpers that return NULL when unset, so a missing identity sees nothing. Membership is re-checked inside the policies with `SECURITY DEFINER` helpers (which also avoid policy recursion), so a forged or stale active-Workspace claim, or a removed member, gains nothing. The table owner is deliberately not `FORCE`d, since the definer helpers rely on bypassing RLS. Consequence: platform data access must happen inside Spring-managed transactions; a bare autocommit statement on the privileged connection would bypass RLS.
